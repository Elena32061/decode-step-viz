# 一次 decode step：8 卡 GB200 上的 81.8446 ms

一个单文件 WebGL 可视化，把一次 LLM decode step 在 8 张 GB200 上的 81.8446 ms
按极慢的速度放出来，用来讲清楚这一步里时间花在哪、数据在卡之间怎么流动。

默认播放速度是真实时间的 **0.001×** —— 一步 81.8 ms 要放 82 秒。慢放本身就是目的。

---

## 怎么运行

三种方式都可以，不需要构建步骤、不需要 npm：

1. **直接双击 `index.html`**（`file://`）。
2. **本地起一个静态服务器**，例如 `python3 -m http.server`，然后打开对应地址。
3. **GitHub Pages**：把这个目录推上去，当静态站点发布即可。

要求：

- 支持 **WebGL2** 的浏览器（较新的 Chrome / Edge / Firefox / Safari）。没有 WebGL2 时页面会给出明确提示，不会留黑屏。
- **需要联网**。three.js r160 通过 CDN（jsDelivr）以 importmap 的方式加载。断网时页面会在 8 秒后提示 three.js 没取到，并说明怎么改成本地加载。

### 为什么 `data.js` 不是 ES module

需求同时要求「双击打开能用」和「数字集中在一个对象里」。ES module 在 `file://`
下会被浏览器的 CORS 规则拦住（`origin: null`），所以 `data.js` 写成传统脚本，
把唯一的数据对象挂在 `globalThis.DECODE_STEP_DATA` 上，`index.html` 里的
module 脚本从那里读。语义上仍然是「一个对象、一处审计」，只是换了交付方式。

## 界面上有什么

**三维场景**

- 8 个 GPU 方块，排成 2 节点 × 4 卡。每个方块内部是该卡 189 GB 显存的分层：
  KV pool 98.5 GB、index key 19.6 GB、其余 70.9 GB。
- 每个 GPU 顶上有 48 个小方块，就是这张卡持有的 48 个专家（8 卡合起来 384 个）。
  MoE 阶段它们会按负载亮起来。
- 下方是 **Grace 主机内存**，Engram 表放在那里，经 NVLink-C2C / RDMA 读回。
- 中间一层网面表示 **NVLink fabric**，画成织物而不是一根根连线。

**三条数据流（粒子）**

- **MoE all-to-all**：dispatch 与 combine 在 8 卡之间穿过 fabric。
  负载重的卡发出更多粒子。
- **Engram RDMA**：step 一开始，Grace 把 L1 和 L14 两层的表同时发出。
  L1 的那批很快被用掉；**L14 的那批会停在卡旁边等很久**，直到 L14 真正执行才被吸进去。
  这段空档就是异步设计生效的证据——数据早就到了，`wait` 只要 4–7 µs。
- **index key 流**：8 个索引器层里，index key 从 HBM 向计算板流动。

**时间条**：40 层按时长铺开，层内按模块着色。索引器层标 ▲，Engram 层标 ●，
L20 单独标出它是候选池的来源。可以直接拖动定位。

**HUD**：当前时刻（µs）、当前层、当前模块，以及一句话说明现在在发生什么。

**点一张 GPU**：右侧出现这张卡的显存分配、行数、专家负载分布和 all-to-all 流量。

**交互**：鼠标拖动旋转 / 滚轮缩放；空格播放暂停；← → 切换层；
速度滑块覆盖 0.0005× 到 1×；三个视角预设（整机 / 单卡 / Grace 链路）。

### 一处刻意的播放行为：Engram wait 会暂留

Engram 的 `wait` 段只有 **5.5 µs**，而默认 0.001× 下一帧要推进 **16.7 µs**，
是它的 **3.0 倍**。照直播放的话，这一段落不落在某一帧上完全看帧相位：扫 1000 种
起始相位，只有 **32.9%** 会落在 wait 上，而且**最多只停一帧**（约 17 ms），
等于看不见。可「wait 只要 4–7 µs」恰恰是这次 profiling 最值得看的发现之一。

所以播放头经过 wait 时会在上面停约 1.1 秒（真实秒表），HUD 同时给出一条
「这一段只有 5.5 µs，比当前速度下的一帧还短，播放已暂留」。

**暂留的是播放，不是被测时间。** HUD 上的 µs 读数始终是真实时刻，时间轴位置也没有
被拉长；手动拖动时间轴或切换层时暂留立即取消。

## 数字的出处

界面上每个数字后面都跟一个小符号，页脚有对照：

| 符号 | 含义 |
|---|---|
| ● 实测 | 来自 profiler。口径：**1 轮、profiler-on、EP8 / 8 卡，8 rank × 8 cycle = 64 个样本**，按 rank-step 求和的 kernel 时长。 |
| ◐ 推导 | 完全由实测值按 `data.js` 里写明的规则算出，不含新信息。 |
| ○ 示意 | 可视化选择，**不是测量值**，不能当结论引用。 |

### 实测的

- 一步总时长 **81.8446 ms**，共 **40 层**。
- 模块拆分（ms / % / kernel launch 数）：MoE 39.4623 / 48.2% / 86；
  注意力核心 11.2302 / 13.7% / 111；注意力投影 10.9542 / 13.4% / 176；
  MHC 超连接 6.0624 / 7.4% / 110；DSA 索引器 4.6245 / 5.7% / 36；
  Eager GEMM 4.1964 / 5.1% / 27；采样·投机·MTP 2.78 / 3.4% / 43；
  Engram 1.73 / 2.1% / 7；其它 0.81 / 1.0%。
- 逐层时间：L2 1.268、L8 1.209、L14 1.195、**L20 2.093**、L24 0.947、
  L28 0.863、L32 0.852、L36 0.854；无索引器的 32 层为 0.524–0.537（取 0.530）。
- 结构：8 个索引器层（L2/8/14/20/24/28/32/36）；Engram 层 L1 与 L14；
  L20 扫描完整 131,072 上下文并建出 16,384 token 候选池（2,048 块 × 8 token），
  L24/28/32/36 复用该池，L20 自己不用；KV 压缩比 L0–L1 无、L2–L19 为 2、L20–L39 为 1。
- 硬件与负载：8 卡 GB200，每卡 189 GB HBM、约 8 TB/s、152 个 SM；
  每卡 320 条请求、131,072 输入 / 512 输出、q8 投机每步 2,560 个查询行；
  KV pool 98.5 GB、index key 常驻 19.6 GB。
- MoE：384 路由专家 + 1 共享专家（融合在同一 kernel）、top-6、每卡 48 专家、
  每卡 15,360 行、平均每专家 320 行、单专家 GEMM `[320,5120]×[5120,2304]`、
  fp8 激活 × fp4 权重；**负载不均衡 max/mean = 1.96×**，理想重排（无副本）为 1.05×；
  all-to-all 每 token 平均去 4.41 张卡、每卡每层出 57.8 MB。
- Engram：表在 Grace 主机内存，每卡每步 122,880 次 RDMA 读（约 31.5 MB）；
  发起这些读要 1.5–1.85 ms 并占满全部 152 个 SM；消费前的 `wait` 只有 4–7 µs。
- DSA：index key 是 FP4（E2M1 + UE8M0 scale），约 72 B/位置；
  每卡每步读 9.06 GB，整步平均 111 GB/s；每个查询行保留 top-512。

### 推导的

这些是用实测值算出来的，规则写在 `data.js` 第 9 节，可以逐条核对：

- **时间轴上每层的起止时刻**，以及层内模块的先后顺序。这是整个可视化里
  最重要的一处推导，详见下一节。
- 每卡显存的「其余」**70.9 GB** = 189 − 98.5 − 19.6。
- 已归类模块的 kernel launch 合计 **596**（八个具名模块相加；`other` 没给 launch 数）。
- Engram 的 1.73 ms 拆成「发起 1.719 ms」+「两次 wait 各 5.5 µs」。
  5.5 µs 取实测区间 4–7 µs 的中点；1.719 ms 落在实测区间 1.5–1.85 ms 内。
- L14 的 Engram 数据按本可视化时间轴落在 **28.6 ms**。

### 示意的（不是测量值）

- **八张卡各自的负载系数**。唯一实测约束是 `max/mean = 1.96×`；
  具体哪张卡最热、其余七张怎么分布，都是为了把不均衡画出来而选的分布
  （均值已归一到 1.00×）。
- **单卡 48 个专家的行数分布**。固定种子生成的偏斜分布，均值与上一条自洽，
  **不是实测直方图**。
- **粒子数量与几何尺寸**：MoE 1,600 个粒子、每卡 36 个 index key 粒子、
  每卡每批 26 个 Engram 粒子、粒子池上限 4,096；方块尺寸、间距、fabric 高度等。
  粒子数量与 57.8 MB 或 4.41 没有定量对应关系，只表示「有流量」和「谁更忙」。
- **停泊粒子被吸入 GPU 的动画时长 0.35 ms**。真实 `wait` 只有 4–7 µs，
  按原尺度根本画不出来，这里放大了。
- **经过 Engram wait 时的暂留 1.1 秒**（真实秒表，见上一节）。
- 默认播放速度 0.001×。

## 时间轴是怎么推出来的（必读）

要有一条能拖的时间轴，就必须把 81.8446 ms 分配到 40 层上。但实测给的是**两组
不同口径**的数字：

- 整步的**模块**拆分（加起来 ≈ 81.85 ms）；
- 逐层的**相对**时间（8 个索引器层 + 32 × 0.530 **只有 26.241 ms**）。

逐层那组显然不是每层的完整墙上时间，它刻画的是层与层之间的轻重。把两组拼起来
的规则如下：

1. Engram 的 1.73 ms 拆成「发起」+ 两次「wait」。发起占满全部 152 个 SM，
   所以放在 step 最开头、与层计算串行。
2. 采样 / 投机 / MTP 的 2.78 ms 放在 40 层之后。
3. DSA 索引器的 4.6245 ms 只分给 8 个索引器层，按「该层实测时间 − 基线 0.530」
   的比例分配。L20 因此拿到最大的一份（1.434 ms）。
4. 剩下的时间按其余模块的实测占比**平均分到 40 层**；层内顺序为
   MHC → (Engram wait) → QKV 投影 → (索引器) → 注意力核心 → 输出投影 →
   Eager GEMM → MoE → 其它。
5. 最后整体缩放一次，使总长严格等于 81.8446 ms。

### 这个推导的三个已知后果

- **层内模块的先后顺序反映的是结构，不是 profiler 记录的 kernel 时序。**
  实测只给了每个模块在整步里的总时长，没有给 kernel 级的时间线。
- **MoE 被平均摊到了 40 层。** 实际各层未必等长。因此时间条上
  「某层的 MoE 从几 ms 到几 ms」是推导位置，不是测量值。
- **L14 的 Engram 空档，实测说法是「约 25 ms」，本时间轴推出来是 28.6 ms。**
  差值来自上一条的平均分摊。两个数字界面上都显示，并分别标了出处。
  这个差值是推导的产物，不是新的测量。

另外，实测表里各模块是四舍五入后给出的，九项相加是 **81.8500 ms**，比总时长
多 **0.0054 ms**。第 5 步的整体缩放吸收了这个残差，没有改动任何实测值
（`data.js` 的 `step.moduleSumResidualMs` 字段把它显式记了下来）。

## 三处值得特别看的地方

1. **MoE 占 48.2%，而且打不开。** dispatch → 专家 GEMM → combine 融合在一个
   kernel 里，profiler 看不到内部。所以这块最大的时间只有一个总数，没有细分。
   界面在 MoE 阶段会把这句话标出来。
2. **Engram 的异步是有效的。** 发起 122,880 次 RDMA 读要 1.5–1.85 ms 并吃掉
   全部 152 个 SM，但真正消费时 `wait` 只有 4–7 µs。L14 的数据在 step 最开始
   就发出，到二十多毫秒后才被用上——可视化里那批停在卡旁边一直不动的粒子就是它。
3. **L20 是转折点。** 它一个人扫完 131,072 的完整上下文，建出 16K 候选池；
   之后的 L24/28/32/36 只在池里打分。这也是它逐层时间（2.093 ms）比其它
   索引器层高出一截的原因。

## 验证了什么、没验证什么

**验证过：**

- `data.js`、页面内的 module 脚本与传统脚本均通过 `node --check` 语法检查。
- `data.js` 的推导自洽（在 Node 里跑过）：292 个时间段，闭合误差 2.8e-14 ms，
  末段 `t1` = 81.8446；推导出的 Engram 发起 1.719 ms 落在实测区间 1.5–1.85，
  两个 wait 各 5.50 µs 落在实测区间 4–7；示意负载分布均值 = 1.0000、
  max/mean = 1.9600，与实测约束一致；单卡 48 专家行数的均值与卡间系数自洽。
- three.js r160 的三个 CDN 地址（主包、OrbitControls、CSS2DRenderer）均返回
  200 且带 `access-control-allow-origin: *`，所以 `file://` 下的跨源 module
  导入不会被拦。
- **在 headless Chrome（软件 WebGL）里真实渲染并截图检查了四个画面**：
  Engram 发起、L20 建池时的 MoE、L14 的 Engram wait，以及点开 GPU 侧栏之后。
  每张都核对过 HUD 的时刻 / 层 / 模块 / 说明 / 注记与时间条播放头的位置。
- 控制台干净：从加载到交互全过程 `window.onerror` 与 `unhandledrejection`
  都没有记录到任何条目。
- **两种打开方式都实测过**：本地 HTTP 服务和直接 `file://` 打开，
  两边都正常启动、场景建成、GPU 侧栏可点开、控制台无报错。
  （`file://` 这条是 `data.js` 写成传统脚本的理由，CDN 的 CORS 头也确认过。）
- 交互：脚本模拟点击命中 GPU 并打开侧栏（6 个分区、48 个专家格、8 条负载条）；
  播放 / 暂停、上一层 / 下一层、重置、速度滑块两端（0.0005× / 1.00×）、
  三个视角预设、窗口 resize 后时间条重建，均无报错。
- 时间轴定位逐段核对过 Engram 发起、L1 wait、L0 MoE、L2 索引器、L14 wait、
  L36 索引器这几个状态，HUD 文案与注记都对得上。
- **wait 暂留那段逻辑做了 9 项断言测试**，测的是从 `index.html` 里抠出来的
  同一段源码（不是复刻版），在 Node 里模拟逐帧推进：两个 wait 都能触发、
  暂留时长 1102 ms 对 1100 ms、暂留后继续前进、同一个 wait 只触发一次、
  从 wait 内部起播也能走出来、1× 速度下整步 135 帧走完不卡住，
  以及上面那两条反证。全部通过。

**修掉的一个真问题：** three.js r160 里 `instanceColor` 只在顶点着色器生效，
片元着色器要 `material.vertexColors` 打开才会用 `vColor`。最初没打开，
导致全部粒子和 384 个专家方块都按材质本色（白色）渲染，整套配色是失效的——
截图才看出来。现已打开 `vertexColors` 并给几何体补了全白的 `color` 属性
（缺这个属性时未绑定的 attribute 取 (0,0,0)，实例会全黑）。

**没验证：**

- **没有做过帧率测量，60 fps 这个目标没有被证实。** 设计规模是「8 个方块 +
  最多约 2,000 个活跃粒子 + 两个 InstancedMesh」，但 headless 里跑的是软件
  WebGL，测出来的帧率没有参考价值，真实 GPU 上的帧率我没有测。
- 没有在 Safari / Firefox 上打开过，也没有在 GitHub Pages 上实际发布过
  （本地 HTTP 服务下是正常的，这是 Pages 最接近的等价场景）。
- 没有做过移动端或窄屏适配验证（CSS 里有一个 1180px 断点，未实测）。
- 鼠标拖动旋转 / 滚轮缩放是 OrbitControls 的默认行为，没有逐一手动试过。
